# 새 프로젝트 시작

원칙: 기능보다 **검증 루프를 먼저** 세운다. 첫 커밋부터 린트·타입 검사·테스트가 초록이고, 하네스가 그것을 지킨다.

## 1. 확인 (한 번에 하나씩 묻는다)

이미 답이 있으면 묻지 않는다.

1. 무엇을, 누구를 위해 만드는가. 첫 버전에서 사용자가 할 수 있어야 하는 한 가지.
2. 제약: 배포 대상, 쓰기로 정해진 언어·프레임워크, 팀 규칙, 예산.
3. 돈·개인정보·외부 발송이 있는가 (있으면 보안·테스트 리뷰어 기준을 높인다).

## 2. 스택 제안

사용자가 정하지 않았으면 두세 가지 선택지를 장단점과 함께 제시하고 하나를 추천한다. 정해지면 바꾸지 않는다. 각 스택의 공식 생성기(`create-next-app`, `npm create vite`, `uv init` 등)를 우선 쓴다.

## 3. 골격 만들기

순서대로, 단계마다 검증 명령이 통과하는지 확인한다.

1. 공식 생성기로 프로젝트 생성, `git init`, 작업 브랜치.
2. 린트·포맷터·타입 검사 설정. `package.json` scripts에 `lint`, `typecheck`, `test`를 둔다.
3. 테스트 러너와 **실제 동작을 단언하는** 테스트 하나.
4. CI: `.github/workflows/ci.yml`에서 `lint` → `typecheck` → `test`. 로컬 게이트와 같은 명령을 쓴다.
5. `.env.example` (이름만, 값 없음). `.gitignore`에 `.env*` 와 `.harness/reviews/`.
6. 하네스:
   - `.harness.json`: 플러그인 `templates/harness.json` 기준으로 위 scripts를 연결. 새 프로젝트이므로 `gates.block: true`.
   - `AGENTS.md`: 플러그인 `templates/AGENTS.md`를 채운다. `CLAUDE.md`에는 `@AGENTS.md`.
   - `.harness/lessons.md`: 빈 파일 (머리말만).

## 4. 첫 기능 한 조각

1단계의 "한 가지"를 `planner`로 계획하고, 테스트 → 구현 → 검증 순으로 만든다. 끝나면 `review` 스킬로 리뷰하고 결과를 보여 준다.

## 5. 마무리

- 만든 것, 실행 방법, 하네스가 지키는 것을 짧게 보고한다.
- 커밋은 로컬까지. 원격 저장소 생성·푸시는 사용자에게 묻는다.
